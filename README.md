## 饭后评估

每种食材均须确认食用比例（0%–500%）。同一顿饭可连续拍多道菜，点击“拍完了”后，再从历史记录按参与者编号选择对应菜品评估。换人拍照前请更换输入的编号；评估页显示这道菜拍照时的原编号和原照片，更换本机编号不会改变已保存记录。草稿自动保存，重新进入可继续；旧记录不强制补评。结果页、详情页和评估页均可删除不存在的食材。

## 匹配规则（对应需求文档）

匹配的单位是**一种食材**：模型拆出几种食材，就做几次独立匹配、返回几条数据。

1. **先按菜名匹配**：识别出的菜名与库中菜名几乎一致时（相似度 ≥0.82），
   **优先在这道菜内部**为每种食材找记录——同一道菜里的「土豆」比别的菜里的「土豆」更贴切；
2. **再按食材匹配**：菜名对不上、或那道菜里没有这种食材时，放开到全库给每条记录打分，
   权重上**食材优先、烹饪方式其次**（0.72 : 0.16，另加 0.12 菜名相似度）；
3. **多个烹饪时间取最长**：同一食材有 6 / 12 分钟两版时一律取 12 分钟那条
   （按食材各自取最久，因为土豆炖牛肉里土豆和牛肉根本没有公共时长）；
4. **切割与下压都测过就都给**：同一食材两种 TPA 测试模式都有数据时，结果页并列展示两组读数；
5. 每种食材各自附一组备选，点一下**只换这一种食材**的数据，不影响其它食材；改选会存进记录。

## 重量估算

照片本身没有任何绝对尺度——同一盘菜拍近拍远，像素面积能差好几倍。所以拍照时必须选
**餐盘直径**，它是整张图里唯一已知的真实长度：

```
盘面积   = π(d/2)²
食材体积 = 盘面积 × 该食材盘面占比 × 平均堆叠厚度
重量     = 体积 × 堆积密度
```

模型只负责**看图量尺寸**（占了盘子多大一片、堆了多厚），克数由小程序端换算，
见 [`miniprogram/utils/weight.ts`](miniprogram/utils/weight.ts)。密度表用的是**堆积密度**
（连缝隙一起算的整堆密度），所以不需要再乘空隙系数——切丝的菜堆得松、整块肉堆得实，
这个差别已经在密度表里了。

模型的直接估重不丢弃，作为第二条路线交叉校验，两者取**加权几何平均**（几何路线 0.7）；
差到 4 倍以上说明至少有一条失灵，退回等权对冲并降低置信度。结果按置信度给出区间
（±30% / ±45% / ±60%），50g 以上按 5g 取整，避免「137g」这种虚假精确。

细节见 [`docs/ai-pipeline.md`](docs/ai-pipeline.md)。

## 数据导出

操作手册见 [识别数据导出](docs/data-export.md)。电脑端导出工具已包含筛选、逐食材展开、质构实测库关联及字段说明，无须重新发布小程序。

```bash
npm run export:demo                 # 用合成示例试运行，不访问云端
npm run export:data -- --input "/完整路径/meal_records.json"
npm run export:cloud                # 已安装CloudBase CLI并执行tcb login后使用
npm run export:full -- --input "/完整路径/meal_records.json" # 全量记录、旧版多菜及补充质构匹配
```

每次输出到 `exports/` 下的新目录，包含识别记录表、食材明细表、质构测试表、字段字典及导出摘要。默认跳过作废记录和被删除食材；未评估数据保留状态，缺失值留空。仅分析完成评估的数据时加 `--completed-only`。原始导出数据及生成文件已加入 `.gitignore`。

## 安全约定

- 千问 API Key 等**真正的密钥**只能放在云函数环境变量，前端代码与仓库不得包含；
- CloudBase 环境 ID 会下发到客户端、非密钥，故 `config.ts` 纳入版本管理；
- `project.private.config.json`、`.env*` 已被 `.gitignore` 忽略；
- 质构数据一律标注为「同类菜肴实测参考值」，不表述为对用户这一份菜的实测或医学建议。
