# AI 分析流程（后端预留）

> 本文档记录后续真实后端的分析流程设计。**当前阶段不调用真实千问 API，也不部署云函数。**
> 前端通过 `services/mealService.ts` 的 mock 实现模拟这一流程。

## 1. 端到端流程

```
图片上传（小程序 → 云存储）
  → 第一次千问识别：菜品、可见食材、烹饪方式、各菜品在图中的区域
  → OpenCV / 几何脚本：根据餐盘直径计算像素-厘米尺度，估算各食物面积
  → 第二次千问综合估算：结合面积、常见份量、密度，给出各食材重量与区间
  → 保存结构化 JSON 到 meal_records
  → 前端读取并展示（用户后续只在前端按比例计算摄入量，不再调用大模型）
```

## 2. 各阶段与状态映射

| 阶段 | 对应 `AnalysisStatus` | 说明 |
| --- | --- | --- |
| 接收任务 | `pending` | 云函数已收到请求 |
| 预处理 | `preprocessing` | 图片解码、压缩、方向校正 |
| 第一次识别 | `stage_1_recognition` | 千问识别菜品/食材/烹饪方式/区域 |
| 几何分析 | `geometry_analysis` | 餐盘尺度标定 + 食物面积计算 |
| 第二次估算 | `stage_2_weight_estimation` | 千问综合估算各食材重量与区间 |
| 完成 | `completed` | 结果写库，前端可读取 |
| 失败 | `failed` | 任一阶段异常 |

前端 `pages/analyzing` 已按上述状态机展示进度，接入真实后端时无需改动展示逻辑。

## 3. 关键约束

- **千问 API Key 只能放在云函数 / 后端环境变量**，不写入任何前端文件或仓库。
- **小程序前端不得直接调用千问**；所有模型调用都经过云函数 `analyzeMeal`。
- **前端不得包含 API Key**（包括 `config.ts`，那里只放云函数名、环境 ID 等非密信息）。
- **重量展示必须为预估值与区间**，并标注「预估结果，仅供记录参考」，不得表现为真实称重或医学建议。
- **用户选择食用比例后无需再次调用大模型**：摄入量在前端按
  `实际摄入 = 预估重量 × 食用比例` 直接计算（见 `utils/weight.ts`）。

## 4. 模型与 prompt 版本

- `MealAnalysis.modelName` / `promptVersion` 字段用于记录每条结果由哪个模型、哪版 prompt 生成，便于后续比对与回溯。
- 建议把模型调用的输入摘要、耗时、token 数写入 `model_logs` 集合。

## 5. 几何分析要点

- 输入：餐盘直径（用户在上传页选择，默认 26 cm）、图片中识别出的餐盘轮廓。
- 用餐盘的已知物理直径标定「像素 → 厘米」尺度，再换算各菜品/食材的投影面积。
- 面积仅为重量估算的一个输入，结合食物类型的常见密度与堆叠高度先验，得到重量区间。
- 局限：堆叠、遮挡、带骨食材的可食比例、油盐酱料无法从单张俯拍图精确还原，故结果始终以区间与可信度呈现。
