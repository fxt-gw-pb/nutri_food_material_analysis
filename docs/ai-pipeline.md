# 识别与质构匹配流程

本版本的目标是：**拍一张菜的照片，认出这是什么菜，拆出它包含的每一种食材，
再为每一种食材各自返回质构库里的实测数据**。
一次识别只出**一道菜**，但这道菜里的食材要列全——匹配的单位是**食材**，
每种食材都是一次独立的匹配，各自有自己的匹配理由、备选和改选入口。
重量估算已重新加入：拍照时用户选**餐盘直径**作为真实尺度，模型只负责看图量几何量
（盘面占比、堆叠厚度），克数由小程序端按「体积 × 堆积密度」换算，见 `utils/weight.ts`
与 README 的「重量估算」一节。

## 1. 总体链路

```
小程序端                              云端
  拍照/选图
  └─ wx.cloud.uploadFile ─────────▶ 云存储 meal-images/
  └─ callFunction analyzeMeal
       action='create'  ───────────▶ 写 pending 记录，秒回 analysisId
       action='process' ───────────▶ 取图片临时地址 → 千问 Qwen-VL 识别
                                      └─ 写回 result.dish + completed
  轮询 status（400ms）
  completed 后跳结果页
  └─ 本地质构匹配（不联网）
       services/textureMatch.ts + data/textureDb.ts
```

**云端只负责「看图说出这道菜的菜名 / 烹饪方式 / 全部食材 / 每种食材的几何量」，只出一道菜。**
注意云端**不给最终克数**：模型对「几克」没有可靠直觉，它只回答「占了盘子多大一片、堆了多厚」，
以及一个仅作交叉校验的直接估重。
识别出的食材是整条链路的主角：每一种都会独立展示、独立匹配一条实测数据。
因此 prompt 明确要求**尽量列全**（通常 2–6 种，上限 10 种），漏掉一种食材，
用户就少看到一条数据。
质构数据的匹配 100% 在手机本地完成：数据库随小程序包下发，换匹配项、看备选、
搜索都不需要再发一次网络请求，老人操作起来是秒回的。

## 2. 云函数 analyzeMeal 的输出契约

```jsonc
{
  "dish": {
    "dishName": "大煮干丝",          // 常见中文标准菜名
    "cookingMethod": "煮",           // 单个简短中文词
    "recognitionConfidence": "high", // high | medium | low
    "weightConfidence": "medium",    // 对整体份量估计的信心
    "ingredients": [                 // 这道菜里的全部食材，每种都会独立匹配并展示
      { "name": "豆腐丝", "cookingMethod": "煮",
        "areaRatio": 0.35,           // 占盘面的面积比例 0–1
        "heightCm": 2,               // 平均堆叠厚度 cm
        "estimatedG": 150 },         // 模型直估，仅作交叉校验
      { "name": "火腿丝", "cookingMethod": "煮",
        "areaRatio": 0.1, "heightCm": 1, "estimatedG": 30 }
    ]
  }
}
```

图里有多样菜时 prompt 要求只输出最主要的那一道；模型仍按 `dishes` 数组返回时，云函数取第一道。
云函数会对 `ingredients` 去重并截到 10 条（与前端 `MAX_QUERY_INGREDIENTS` 对齐）。
葱姜蒜等纯调味配料要求不列入。模型没拆出食材时，用菜名本身兜底成一条 ingredient，
保证前端至少能做一次匹配。识别不到食物时返回 `{"dish": null}`。

## 3. 本地质构数据库

- 原始表：`scripts/source/500道菜肴质构数据_切割测试_下压测试分类.xlsx`
  （496 道菜、454 种食材、712 条 TPA 测试记录、7 个菜品类别）。
- 编译脚本：`scripts/build-texture-db.py` → `miniprogram/data/textureDb.data.ts`（约 133 KB）。
- 新表已有独立的**「食材」「烹饪方式」「时间」**列，脚本直接读列即可，
  不必再解析「源文件名」——旧版那套文件名拆分逻辑已删除。
- 新表分 **`切割测试` / `下压测试`** 两个 sheet，是同一食材的两种 TPA 测试模式。
  两个 sheet 都编译进同一张表，用 `testMode` 字段区分（切割 653 行 / 下压 59 行）。
  下压测试覆盖的 59 道菜全部是切割测试的子集，所以这 59 道菜的对应食材会有两组读数。
- 索引有两套：`byDish`（菜名）与 `byIngredient`（归一化食材名）。

改了原始 xlsx 之后重新生成：

```bash
python3 scripts/build-texture-db.py
```

## 4. 匹配规则

`miniprogram/services/textureMatch.ts`：

**匹配的单位是「一种食材」。** 模型拆出 N 种食材，就做 N 次独立匹配，返回 N 条数据。
（旧版以「整道菜」为单位只返回一条，已废弃。）

**第一步 · 菜名匹配。** 识别出的菜名与库中菜名相似度 ≥ 0.82 即视为「几乎一致」。
此时**优先在这道菜内部**为每种食材找对应记录——同一道菜里的「土豆」显然比别的菜里的
「土豆」更贴近用户盘子里的那一份。食材相似度 ≥ 0.5 即采纳。

**第二步 · 食材匹配。** 菜名对不上（或那道菜里没有这种食材）时，放开到全库为
**每条记录**打分：

```
总分 = 0.72 × 食材相似度 + 0.16 × 烹饪方式接近度 + 0.12 × 菜名相似度
```

权重体现需求里的「**食材优先，烹饪方式其次**」。烹饪方式接近度：完全一致 1，
同族（煮/炖/焖/煲 属同族）0.5，库中未标注 0.3，不同族 0。
总分低于 0.34 视为没匹配上，此时不自动选中，但仍把最接近的几条列为备选。
食材相似度 ≥ 0.95 标为「精确匹配」，否则标「相近食材」。

食材相似度专门为中文食材名做了处理（`utils/similarity.ts`）：字/二元组 Dice、
包含关系，以及**同品类尾字加成**——「基围虾」和「鲜虾」字面几乎不重合，但尾字同为
「虾」，按「食材优先」的原则应当能互相捞到。比较前先剥掉刀工后缀（丝/片/块/丁/仁…）
和**器具词**（高压锅/空气炸锅/砂锅…），因为库里有「鸭肉高压锅」这类把器具粘进
食材名的写法，不剥的话「鸭肉」就匹配不上它。

对 9 月 28 日反馈增加了少量有实物依据的特例：花生米与花生仁同义，但花生芽不能当作花生仁；馒头等成型主食被旧模型拆成面粉时，按成品菜名寻找参考值；韭菜煎蛋与韭菜摊鸡蛋按同义菜名比较。配方或烹饪方式与参考记录不同仍提示复核；历史人工改选保留，并在跨食材改选时提醒核对。

**规则一 · 多个烹饪时间取最长。** 同一道菜、同一种食材、同一烹饪方式有 6 分钟和
12 分钟两版时，一律取时间更长的那条。落地在两处：编译时按时长降序排，运行时
`betterThan()` 在同分场景里优先长时间，`dedupe()` 在生成备选时也只保留最长的那条。

**规则二 · 切割与下压都测过就都给。** `alternateTestModes()` 找出同菜、同食材、
同烹饪方式但测试模式不同的记录，结果页把两组读数并列展示（切割在前），
让用户看到同一食材在两种受力方式下的差别。

**规则三 · 逐食材备选与改选。** 每种食材都各自附一组备选记录（带匹配度与理由），
点一下就只换这一种食材的数据，不影响其它食材；也能输入关键词在全库搜食材或菜名。
用户的改选存进 `selectedRecords`（识别食材名 → 记录 id 的映射，只存被改过的那几种），
匹配本身每次打开都现算——质构库以后升级了，老记录也会自动用上新结果。

## 5. 展示口径

结果页按「这道菜 → 每种食材一张卡」展示，每张卡都给老人看得懂的三句话，
并可展开九项完整指标（硬度、脆度、黏着性、弹性、咀嚼性、胶着性、内聚性、回复性、样品高度）。
同一食材若切割与下压都测过，两组读数上下并列：

| 展示 | 依据 | 档位 |
| --- | --- | --- |
| 软硬 | 硬度 gf | 很软 <200 / 偏软 <420 / 适中 <800 / 偏硬 <1600 / 很硬 ≥1600 |
| 嚼起来 | 咀嚼性 gf | 很好嚼 <10 / 好嚼 <30 / 一般 <80 / 偏费劲 <180 / 很费劲 ≥180 |
| 黏牙 | 黏着性绝对值 | 不黏牙 <2 / 略黏牙 <10 / 较黏牙 ≥10 |

阈值取自本数据库自身的分位数，**不是医学标准**。页面统一标注：数据来自实验室对
同类食材样本的 TPA 测试，不等同于用户这一份菜的实测值，也不构成医学建议。

## 6. 安全约束

- 千问 API Key **只能**放在云函数环境变量 `DASHSCOPE_API_KEY`，前端代码与仓库绝不包含。
  换 Key 的操作步骤见 [`deploy-and-apikey.md`](./deploy-and-apikey.md)。
- 上传的照片存于用户自己的云存储，删除记录时一并删除。
