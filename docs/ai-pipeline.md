# 识别与质构匹配流程

本版本的目标是：**拍一张菜的照片，告诉用户这道菜（及其各种原食材）软不软、好不好嚼**。
不再估算任何重量——实测表明图像估重误差过大，已整条移除。

## 1. 总体链路

```
小程序端                              云端
  拍照/选图
  └─ wx.cloud.uploadFile ─────────▶ 云存储 meal-images/
  └─ callFunction analyzeMeal
       action='create'  ───────────▶ 写 pending 记录，秒回 analysisId
       action='process' ───────────▶ 取图片临时地址 → 千问 Qwen-VL 识别
                                      └─ 写回 result.dishes + completed
  轮询 status（400ms）
  completed 后跳结果页
  └─ 本地质构匹配（不联网）
       services/textureMatch.ts + data/textureDb.ts
```

**云端只负责「看图说出菜名 / 烹饪方式 / 原食材」，一句重量都不提。**
质构数据的匹配 100% 在手机本地完成：数据库随小程序包下发，换匹配项、看备选、
搜索都不需要再发一次网络请求，老人操作起来是秒回的。

## 2. 云函数 analyzeMeal 的输出契约

```jsonc
{
  "dishes": [
    {
      "dishName": "大煮干丝",          // 常见中文标准菜名
      "cookingMethod": "煮",           // 单个简短中文词
      "recognitionConfidence": "high", // high | medium | low
      "ingredients": [
        { "name": "豆腐丝", "cookingMethod": "煮" },
        { "name": "火腿丝", "cookingMethod": "煮" }
      ]
    }
  ]
}
```

模型没拆出食材时，云函数会用菜名本身兜底成一条 ingredient，保证前端至少能做一次食材匹配。

## 3. 本地质构数据库

- 原始表：`scripts/source/500道菜肴质构数据整合.xlsx`（496 道菜、712 条去重后的 TPA 测试记录）。
- 编译脚本：`scripts/build-texture-db.py` → `miniprogram/data/textureDb.data.ts`（约 131 KB）。
- 解析核心是表里的**「源文件名」**列，形如
  `粉丝鲜虾煲12分钟—鲜虾—（TPA全质构切割测试）.xlsx`，从中拆出
  **菜名 / 原食材名 / 烹饪方式 / 烹饪时间（分钟）**。
- 原表把整份数据粘贴了两遍，脚本会去掉完全重复的行。

改了原始 xlsx 之后重新生成：

```bash
python3 scripts/build-texture-db.py
```

## 4. 匹配规则（对应需求文档三条）

`miniprogram/services/textureMatch.ts`：

**第一步 · 菜名匹配。** 识别出的菜名与库中菜名相似度 ≥ 0.82 即视为「几乎一致」，
直接采用该菜的数据，并按原食材拆成多项（如大煮干丝 → 火腿丝 + 豆腐丝）。

**第二步 · 食材匹配。** 菜名对不上时，用识别出的原食材 + 烹饪方式在全库打分：

```
总分 = 0.78 × 食材相似度 + 0.18 × 烹饪方式接近度 + 0.04 × 菜名相似度
```

权重体现需求里的「**食材优先，烹饪方式其次**」。烹饪方式接近度：完全一致 1，
同族（煮/炖/焖/煲 属同族）0.5，库中未标注 0.3，不同族 0。
总分低于 0.34 视为没匹配上，此时不自动选中，但仍把最接近的几条列为备选。

食材相似度专门为中文食材名做了处理（`utils/similarity.ts`）：字/二元组 Dice、
包含关系，以及**同品类尾字加成**——「基围虾」和「鲜虾」字面几乎不重合，但尾字同为
「虾」，按「食材优先」的原则应当能互相捞到。刀工后缀（丝/片/块/丁/仁…）先剥再比。

**第三条 · 同菜多时长取更久的。** 同一道菜、同一种食材有 6 分钟和 12 分钟两版时，
一律优先取时间较久的那条（`preferLongerCooking`，以及同分排序时按时长降序）。

**备选与改选。** 每一项都带一组备选，结果页展示在下方，老人可以直接点选换掉；
还能输入关键词在全库搜索。用户的改选存进 `selections`（只存 recordId），
匹配本身每次打开都现算——数据库以后升级了，老记录也会自动用上新结果。

## 5. 展示口径

九项指标（硬度、脆度、黏着性、弹性、咀嚼性、胶着性、内聚性、回复性、样品高度）在
详情页完整列出；结果页只给老人看得懂的三句话：

| 展示 | 依据 | 档位 |
| --- | --- | --- |
| 软硬 | 硬度 gf | 很软 <200 / 偏软 <420 / 适中 <800 / 偏硬 <1600 / 很硬 ≥1600 |
| 嚼起来 | 咀嚼性 gf | 很好嚼 <10 / 好嚼 <30 / 一般 <80 / 偏费劲 <180 / 很费劲 ≥180 |
| 黏牙 | 黏着性绝对值 | 不黏牙 <2 / 略黏牙 <10 / 较黏牙 ≥10 |

阈值取自本数据库自身的分位数，**不是医学标准**。页面统一标注：数据来自实验室对
同类菜肴样本的 TPA 测试，不等同于用户这一份菜的实测值，也不构成医学建议。

## 6. 安全约束

- 千问 API Key **只能**放在云函数环境变量 `DASHSCOPE_API_KEY`，前端代码与仓库绝不包含。
  换 Key 的操作步骤见 [`deploy-and-apikey.md`](./deploy-and-apikey.md)。
- 上传的照片存于用户自己的云存储，删除记录时一并删除。
